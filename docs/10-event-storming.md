# 10. イベントストーミング（Phase B）

ADR-0006 で採用した手法に基づく、ドメインイベントの洗い出し結果。

対象スコープ：**生産指示 + 実績収集 + 在庫/ロットトレース**（およびそれに必要なマスタ）

## 手順

```
1. 混沌の探索    思いつく限りのイベントを過去形で書き出す（順序は気にしない）
2. 時系列に並べる 因果の順に整理し、矛盾とホットスポットを見つける   ← 完了
3. 転換点の特定   業務の意味が切り替わる箇所 ＝ 境界の最有力候補
4. 境界の候補    転換点とイベントの塊から Bounded Context を引く
```

## イベント一覧（時系列）

★ は転換点候補。各グループには**変更理由**を併記している。
ADR-0007 で決めた駆動軸が「変更の波及範囲」であるため、
**変更理由が変わるところが境界の候補**になる。

## 落としたイベントと理由

| 落としたもの | 理由 |
| --- | --- |
| ロットが追跡された | **業務の状態を何も変えないため、ドメインイベントではない。** これは読み取りモデル（クエリ）であり、Phase D-2 で扱う。イベントストーミングで最初に混入しやすいノイズの典型 |
| 品目が更新された／削除された | CRUD イベントの羅列は、ただのテーブル一覧であり境界を示さない（ADR-0006 の失敗パターン）。業務的に意味のある「BOM が改訂された」のみ残した |

## ホットスポット

イベントストーミングでは、意見が割れる箇所（ホットスポット）が最重要である。
そこが設計の分岐点だからである。

| ID | ホットスポット | 状態 |
| --- | --- | --- |
| HS-1 | E2「材料が消費された」— いつ・どうやって計上するか | 解決 → [ADR-0008](adr/0008-material-consumption-reporting.md) |

## 次のステップ

- 手順3（転換点の特定）と手順4（境界の候補）は Phase C-1 で行う
- その前に B-3（ユビキタス言語の整理）で、
  **同じ言葉が文脈によって意味を変える箇所**を洗い出す。
  意味が変わる場所は、境界の強い証拠になる
