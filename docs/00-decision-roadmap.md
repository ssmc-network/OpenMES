# 00. 意思決定ロードマップ

このドキュメントは「**何を、どの順番で決めるか**」を管理する。
マイクロサービス設計における意思決定の順序そのものを学ぶことが、
本プロジェクトの目的の1つであるため、進捗と決定内容をここに集約する。

## なぜ「順序」が重要なのか

マイクロサービス化の失敗の多くは、**決める順番を間違えたこと**が原因になる。

典型的な失敗の順序はこうなる。

```
1. 「マイクロサービスにしよう」と決める      ← 手段が目的化
2. 技術スタックとインフラを選定する          ← まだドメインを理解していない
3. 既存のテーブル構成を見てサービスに割る     ← データ駆動の分割
4. 作ってみたら、1つの操作で全サービスを呼ぶ  ← 分散モノリスの完成
5. 「マイクロサービスは失敗だった」と結論     ← 分割の仕方が失敗しただけ
```

正しくは、**ドメインの理解 → 境界の決定 → データ所有の決定 → 通信と整合性 → 技術選定**
の順に進む。技術選定は驚くほど後ろに来る。

> 補足：Claude は当初このプロジェクトで「まず技術スタックを決めましょう」と提案したが、
> これはまさに上記の失敗パターン2にあたる。順序を修正した。

## 全体マップ

```
Phase A  分けるかどうかを決める
  A-1  そもそも分割が必要か / どこから作り始めるか
  A-2  分割の駆動軸（何を最適化するために分けるのか）

Phase B  ドメインを理解する
  B-1  境界の発見手法を選ぶ
  B-2  業務フローとドメインイベントを洗い出す
  B-3  ユビキタス言語を整理する（同じ言葉の意味が変わる場所を探す）

Phase C  境界を決める
  C-1  境界づけられたコンテキストを特定する
  C-2  コンテキストマップを描く（依存の向きと関係の種類）
  C-3  サービス境界の候補を複数作り、評価軸で比較する
  C-4  集約とトランザクション境界を確定する   ← ここで DB 分割の可否が見える

Phase D  データとやり取りを決める
  D-1  データの所有権（誰が正本を持つか）
  D-2  他コンテキストのデータの参照方法（同期照会 / 複製 / スナップショット）
  D-3  通信方式（同期 / 非同期、REST / gRPC / MQ）
  D-4  整合性の担保方式（Saga、Outbox、冪等性）

Phase E  実装の器を決める
  E-1  DB 分離の物理形態（別インスタンス / スキーマ / 論理分離）
  E-2  技術スタック                          ← ここでようやく技術の話
  E-3  レイヤ構成とトランザクション境界の実装方式
  E-4  テスト戦略と CI

Phase F  実装

Phase G  検証と振り返り
```

## 2ラウンド構成（ADR-0005 により決定）

A-1 の決定により、Phase F（実装）以降は2ラウンドに分かれる。

```
第1ラウンド  1プロセス・N スキーマ
             DB 分割そのものが成立するかを検証する
             越境は DB のロール権限が拒否する
                    │
                    ▼
第2ラウンド  プロセスを分割
             ネットワーク越しの通信、部分障害、Saga、
             デプロイ独立性を検証する
```

**第1ラウンドの結果だけで「分割できた」と結論してはならない。**
1プロセス内ではトランザクションが閉じるため、Saga なしでも整合性が取れてしまう。
これは ADR-0005 のリスク R-A として記録済み。

## 現実にはウォーターフォールではない

上の順序は「初回に通す道筋」であって、実際は行き来する。

- C-4（トランザクション境界）で「この2つは同一トランザクションが必要」と判明したら、
  C-1（コンテキスト特定）に戻って境界を引き直す
- D-4（Saga）の実装量が膨れたら、それは境界が間違っているサインなので C に戻る
- F（実装）で分かることも多い。**戻ることは失敗ではなく、想定された動き**

重要なのは「**戻れる順序で決めていく**」こと。
技術スタックを先に決めると、その制約に境界を合わせてしまい、戻れなくなる。

**破棄の理由**: 成果物としては成立していたが、Claude が意思決定を先回りして
確定させたものであり、利用者が設計判断を経験する機会が失われていた。

内容は git 履歴（コミット `dfea945`）に残っている。
同じ論点を再検討する際、**先入観を避けるため、原則として参照しない**。
比較したい場合は、自分で結論を出した後に見ること。

**ADR 番号の扱い**: 破棄した ADR-0001〜0003 の番号は再利用しない（欠番のままにする）。
ADR は「その時点で何を考えていたか」の記録であり、番号が指す対象が
後から変わると履歴が追えなくなるため。次に作成する ADR は 0005 から始める。
