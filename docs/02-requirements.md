# 02. 要件定義

## 1. スコープ

### 1.1 対象業務

離散製造（部品加工・組立）を想定し、以下の業務を対象とする。

- **マスタ管理** — 品目、BOM（部品表）、工程（ルーティング）、作業区、保管場所
- **生産指示** — 製造オーダーの登録、工程展開、所要材料の算出、リリース
- **実績収集** — 作業の開始／完了、良品数・不良数の報告、材料消費の記録
- **在庫・ロット管理** — 引当、払出、入庫、ロット採番、ロット系譜による前後追跡

### 1.2 対象外（明示的に作らない）

検証の焦点をぼかさないため、以下は範囲外とする。

- 生産計画・スケジューリング（オーダーは外部から与えられる前提）
- 設備連携（PLC / OPC-UA / SCADA）
- 品質検査・SPC・不適合管理（不良数の記録のみ行う）
- 保全管理、原価計算、人員管理、ERP連携
- 認証・認可の本格実装（検証に必要な最小限のみ）
- マルチテナント、多言語対応、帳票出力

### 1.3 前提

- 対象は単一工場・単一ライン
- 製造オーダーは1品目・1ルーティングに対して発行される
- 材料は「ロット管理品」と「非ロット管理品」の両方が存在する
- 在庫は「保管場所（ロケーション）× 品目 × ロット」単位で保持する

## 3. 業務フロー（正常系）

```
[マスタ管理者]  品目・BOM・工程を登録
                          │
[生産管理者]    製造オーダー登録  ── 品目/BOM/工程の妥当性をマスタに照会
                          │        所要材料を算出してオーダーに保持
                          ▼
[生産管理者]    オーダーをリリース ── 在庫に対して材料を引当
                          │
                          ▼
[現場作業者]    作業開始（工程単位）
                          │
[現場作業者]    材料消費を報告   ── 引当ロットから在庫を払出
                          │
[現場作業者]    作業完了を報告   ── 良品数・不良数を計上
                          │        最終工程なら完成品ロットを採番し入庫
                          │        消費した材料ロット → 製品ロットの系譜を記録
                          ▼
[品質担当者]    ロットトレース   ── 前方/後方に系譜を辿る
```

## 5. ユースケース詳細（検証上重要なもの）

### UC-03 製造オーダーを登録する

**目的**: 製造すべき品目・数量・納期を確定し、工程と所要材料を展開する。

**手順**
1. 生産管理者が 品目コード / 数量 / 納期 を指定して登録を要求する
2. order サービスは master サービスに対し、品目の存在・有効な BOM・有効なルーティングを照会する
3. 取得した BOM から所要材料量（数量 × 員数 × (1 + 歩留ロス率)）を算出する
4. 取得したルーティングから工程行を展開する
5. **参照したマスタの内容をオーダーにスナップショットとして保持する**
6. オーダーを `CREATED` 状態で確定する

**検証論点**
- master は別スキーマのため JOIN できない。API 経由の照会のみで成立するか
- マスタが後から変更されても、発行済みオーダーの内容が変わってはならない → スナップショット保持が必要
- master サービスが停止している間、オーダー登録はできなくなる（可用性の結合）。これを許容するか

**例外**
- 品目・BOM・ルーティングが存在しない、または有効期間外 → 登録を拒否
- master サービスが応答しない → 登録を拒否し、リトライ可能なエラーを返す

### UC-04 製造オーダーをリリースする

**目的**: 所要材料を在庫から引き当て、作業開始可能な状態にする。

**手順**
1. order サービスがオーダーの所要材料リストを取り出す
2. inventory サービスに対し、オーダー番号を参照キーとして引当を要求する（冪等キー付き）
3. inventory サービスは在庫から引当可能なロットを選定し、引当済数量を増やす
4. order サービスはオーダーを `RELEASED` に更新し、引当結果をローカルに記録する

**検証論点**
- 引当の真実は inventory 側にある。order 側が保持するのは参照用のコピーに過ぎない
- 引当成功後に order 側の更新が失敗した場合、引当を取り消す補償が必要（Saga）
- 同じリリース要求が二重に来ても二重引当しないこと（冪等キー）

**例外**
- 在庫不足 → 引当を行わず、不足品目を返してリリースを拒否
- 引当成功後の order 更新失敗 → 引当解除の補償を実行

### UC-07 作業完了を報告する

**目的**: 良品数・不良数を計上し、最終工程であれば完成品を入庫してロット系譜を記録する。

**手順**
1. execution サービスが作業実績（良品数・不良数・終了時刻）を記録する
2. order サービスに工程の進捗（完了数量・工程ステータス）を通知する
3. 最終工程の場合、inventory サービスに完成品の入庫を要求する
   - 完成品ロットを採番する
   - 当該オーダーで消費された材料ロット群を親として、系譜を記録する
4. 全工程完了なら order サービスがオーダーを `COMPLETED` に更新する

**検証論点**
- 1つの現場操作が3サービスにまたがる。**ここが分割の成否を最も強く決める**
- 途中で失敗した場合の補償（実績の取消 / 入庫の取消）が現実的に書けるか
- 現場は「完了ボタンを押したら終わる」ことを期待する。同期でどこまで待たせるか

**例外**
- inventory サービス障害 → 実績は記録済みとし、入庫を後続で再実行（結果整合）か、実績ごと取り消す（即時整合）かを設計判断として検証する

### UC-09 ロットを前方/後方トレースする

**目的**: 品質問題発生時に、影響範囲を特定する。

- **後方トレース（Where-from）**: 指定した製品ロットが、どの材料ロットから作られたかを遡る
- **前方トレース（Where-used）**: 指定した材料ロットが、どの製品ロットに使われたかを辿る

**手順**
1. 起点ロット番号と方向・最大階層数を指定する
2. inventory サービスがロット系譜を再帰的に探索する
3. 各階層のロット・数量・関連オーダー番号を返す

**検証論点**
- 系譜情報を inventory スキーマ内に閉じ込められるか。閉じ込められれば再帰CTE 1回で済む
- 系譜の記録元は execution（どの材料を消費したか）である。**記録の責務と探索の責務をどちらのサービスに置くか**が設計の分岐点
- 階層が深い場合の性能

### UC-10 オーダー進捗を照会する

**目的**: オーダーの計画・実績・在庫状況を1画面で確認する。

**必要な情報**
- オーダー基本情報・工程一覧（order）
- 工程ごとの実績数量・稼働状況（execution）
- 引当状況・完成品入庫状況（inventory）

**検証論点**
- 3サービスへの並行呼び出しで組み立てる（API composition）
- 一覧画面（複数オーダー）で N+1 が発生しないか。発生する場合、バルク取得APIで回避できるか
- 回避できない場合、読み取り専用の集約ビュー（CQRS）が必要になる → 仮説 H5 の棄却

## 6. 機能要件

| ID | 要件 |
| --- | --- |
| FR-01 | 品目・BOM・ルーティング・作業区・保管場所を登録／照会できる |
| FR-02 | BOM とルーティングは有効期間を持ち、指定日時点で有効な版を解決できる |
| FR-03 | 製造オーダーを登録し、工程と所要材料を自動展開できる |
| FR-04 | オーダー登録時に参照したマスタ内容をスナップショットとして保持する |
| FR-05 | オーダーをリリースし、所要材料を在庫から引き当てられる |
| FR-06 | 在庫不足時はリリースを拒否し、不足品目と不足数を返す |
| FR-07 | 工程単位で作業の開始・完了を記録できる |
| FR-08 | 作業完了時に良品数・不良数（不良コード別）を記録できる |
| FR-09 | 材料消費をロット単位で記録し、在庫を払い出せる |
| FR-10 | 最終工程完了時に完成品ロットを採番し、入庫できる |
| FR-11 | 消費した材料ロットと生成した製品ロットの系譜を記録する |
| FR-12 | 任意のロットについて前方／後方トレースを実行できる |
| FR-13 | オーダーの進捗（工程別の計画数・実績数・状態）を照会できる |
| FR-14 | 全ての在庫変動は取引履歴として追記され、遡って参照できる |
| FR-15 | 実績報告・引当・入庫は冪等キーにより二重実行を防止する |

## 7. 非機能要件

| ID | 分類 | 要件 |
| --- | --- | --- |
| NFR-01 | データ分離 | 各サービスは自スキーマ以外のテーブルに一切アクセスできない（DBロール権限で強制） |
| NFR-02 | データ分離 | スキーマを跨ぐ外部キー制約を持たない |
| NFR-03 | 整合性 | サービスを跨ぐ更新は Saga により、失敗時に補償される |
| NFR-04 | 整合性 | 在庫数量は負にならない |
| NFR-05 | 冪等性 | 更新系APIは冪等キーを受け付け、同一キーの再実行で状態が変化しない |
| NFR-06 | 可観測性 | 全リクエストに相関IDを付与し、サービスを跨いで追跡できる |
| NFR-07 | 監査性 | 在庫変動・実績・オーダー状態遷移は履歴として保持する |
| NFR-08 | 性能 | UC-10（単一オーダー進捗照会）の p95 応答時間の閾値を Phase 1 で設定し、以降計測する |
| NFR-09 | 性能 | ロットトレース（5階層・各階層10ロット）が実用的な時間で完了する |
| NFR-10 | 再現性 | 環境構築からE2Eテスト完走までがコマンド1つで再現できる |
| NFR-11 | テスト容易性 | 各サービスは他サービスをスタブ化して単体で起動・テストできる |
