# ADR-0008: 材料消費は都度実績入力（ロット指定）で計上する

- ステータス: 採用
- 日付: 2026-08-19
- 対応ステップ: B-2（ホットスポット HS-1）

## 背景

イベント E2「材料が消費された」について、
いつ・どうやって消費を計上するかは MES の古典的なホットスポットである。
方式によってイベントの構造が変わり、サービス境界にも影響する。

## 決定

**都度実績入力**を採用する。
作業者が、消費した材料をロット番号と数量を指定して都度報告する。

## 検討した代替案

### 案2: バックフラッシュ

完成数量の報告時に、BOM から所要量を逆算して自動計上する。
現場の入力負荷がほぼゼロで実装もシンプルだが、
**ロット単位の追跡ができない**。

本プロジェクトの検証対象にロットトレースが含まれているため、
これを選ぶと**検証対象そのものが消える**。→ 棄却

実務での典型的な失敗として、トレーサビリティ要件があるのに
バックフラッシュを選び、リコール時に追跡できない事例がある
（食品・医薬・自動車）。また BOM と実使用量の乖離により
在庫差異が蓄積し、差異の発生箇所も特定できなくなる。

### 案3: ハイブリッド（ロット管理品のみ都度、他はバックフラッシュ）

**製造業では最も多い実務パターン**であり、
現場負荷と精度のバランスが良い。

しかし2方式が同居するため、品目ごとの方式判定が必要になり、
その判定ルール自体がマスタに乗る。結果として
**境界の議論が濁る**。検証プロジェクトとして論点を絞りたいため
今回は不採用とした。→ 棄却（実務性は認める）

## 決定の理由

1. 検証対象にロットトレースが含まれており、案1 でなければ検証できない
2. 論点を絞れる。方式が1つなので境界の議論が濁らない
3. **案1 が最もイベント数が多く、トランザクション境界が最も厳しく問われる。**
   検証として一番きつい条件になるため、成立すれば結論が強くなる

## この選択が抱えるリスク

| リスク | 内容 |
| --- | --- |
| 現場の入力負荷 | 実運用では入力手段（バーコード等）がないと破綻する。本プロジェクトは検証目的のため UI 負荷は評価対象外とするが、**「実運用ではこの前提が必要」として検証レポートに明記する** |
| イベント数の増加 | 実装対象が増える。ただしこれは意図した選択である（トランザクション境界を厳しく問うため） |

## 結果

- E2「材料が消費された」は、E4「作業が完了した」に従属しない**独立したイベント**になる
- 消費のたびに在庫の払出が発生するため、
  **実行と在庫のあいだにトランザクション境界の問題が明確に立つ**
- ロット系譜（P3）の情報源が E2 になる。
  どのロットを消費したかが記録されるため、追跡が成立する
