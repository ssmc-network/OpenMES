# ADR-0004: 開発の進め方（Claude との協働モード）

- ステータス: 採用
- 日付: 2026-08-19

## 背景

本プロジェクトには、README に記載した「Database per Service の検証」に加えて、
**利用者本人のスキル向上**という目的がある。

当初 Claude は、要件定義からアーキテクチャ設計・ADR-0001〜0003 までを
単独で確定させて提示していた。成果物としては成立するが、
**利用者が設計判断を経験する機会が失われる**ため、この目的に対しては逆効果だった。

そこで協働の進め方そのものを設計対象として決定する。

## 決定

| 項目 | 決定 |
| --- | --- |
| 実装の主体 | Claude が実装し、設計意図の解説を添えて利用者がレビューする |
| 質問の粒度 | 大きな設計判断に加え、**実装パターンの選択**（ORM/生SQL、エラー処理方式、DI、テスト構造など）も選択肢として提示する |
| 解説の深さ | 選択肢のメリデメに加え、**実務での失敗例・アンチパターン**まで含める |
| 重点領域 | ①分散システム/MSA設計 ②DB設計・SQL ③API設計・アプリケーション層 ④**データアクセス層とトランザクション境界の接続方式**（Outbox / Saga / MQ による交通整理を含む） |

実運用ルールの詳細は `CLAUDE.md` の「進め方」節に記載する。

## 検討した代替案

**案A: Claude が全て実装し、利用者は成果物だけ受け取る**
進度は最速。だが「読めるが書けない・判断できない」状態になり、目的を達成しない。→ 棄却

**案B: 利用者が実装し、Claude はレビューのみ**
定着は最も深い。しかし4サービス分の実装量に対して、
検証の結論に到達する前に力尽きるリスクが高い。→ 今回は棄却

**案C: 案A と案B の中間（採用）**
実装は Claude が担うが、**判断は利用者が下す**。
判断の材料（選択肢・メリデメ・失敗例）を Claude が揃える責任を負う。
検証プロジェクトとしての完走可能性と、学習効果を両立させる。

## 結果

- 実装速度は意図的に落ちる。これはコストではなく設計上の選択である
- 「1つの論点 → 質問 → 合意 → 実装 → 解説」を小さく回す
- 利用者が選んだ選択肢と理由は ADR に残す。**推奨と異なる選択がされた場合も、その案で完遂する**
- 既に Claude が単独で決めた ADR-0001〜0003 についても、
  利用者が判断し直したいと表明した場合は選択肢の提示からやり直す
