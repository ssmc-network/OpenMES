# ADR-0002: ロット系譜は inventory サービスが保持する

- ステータス: 採用
- 日付: 2026-08-19

## 背景

ロットの前方/後方トレース（UC-09）を成立させるには、
「どの材料ロットからどの製品ロットができたか」の系譜が必要になる。

系譜のもとになる事実は2つある。
- 材料を消費したという事実 → execution サービスが知る
- ロットを採番し在庫を増減したという事実 → inventory サービスが知る

どちらが系譜を保持すべきかで、トレースの実装難度が大きく変わる。

## 決定

**inventory サービスが `lot_genealogy` を保持する。**

execution サービスは「この作業でこの材料ロットをこれだけ消費した」を
払出API経由で inventory に伝えるにとどめる。
完成品入庫時に、inventory 側で当該オーダーの消費ロット群を親として系譜を記録する。

## 検討した代替案

**案A: execution が保持する**
消費を記録するのは execution なので一見自然。
しかしトレース時にロットの属性（品目・数量・入庫元）を inventory に問い合わせる必要があり、
再帰探索がサービスを跨ぐ。階層ごとに往復が発生し、N+1 になる。→ 棄却

**案C: トレース専用サービスを作る**
イベント駆動で系譜を集約する読み取り専用サービス。設計としては妥当だが、
サービス数が増えミニマム構成の趣旨から外れる。また非同期基盤の導入が前提になる。→ 今回は棄却

## 結果

- トレースが `mes_inventory` スキーマ内の再帰CTE 1回で完結する
- execution は系譜の存在を知らなくてよい（責務が薄くなる）
- 一方、inventory が「オーダー単位で消費ロットを集計する」責務を負う
  → 払出時に `ref_no`（オーダー番号）を必ず受け取る設計が必須になる

**検証で確認すること**: トレース結果に品目名など master 由来の情報を含めたくなった場合に、
どの程度の追加参照が発生するか（H4 の判定材料）。
