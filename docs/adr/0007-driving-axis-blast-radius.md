# ADR-0007: 分割の駆動軸は「変更の波及範囲の局所化」とする

- ステータス: 採用
- 日付: 2026-08-19
- 対応ステップ: A-2（分割の駆動軸）

## 背景

このプロジェクトを始めた実際の動機は、利用者が参画している実プロジェクトにおいて

> **DB がモノリスかつ複雑で、1つの修正の波及範囲が誰にも分からない状態になっている**

という問題を抱えていることにある。

当初 Claude は A-2 を「検証と学習」と記載していたが、
これは**プロジェクトの目的**であって**分割の駆動軸**ではない。
駆動軸とは「何を最適化するために分けるのか」であり、これが境界の引き方を決める。

## 決定

分割の駆動軸を **変更の波及範囲の局所化（blast radius containment）** とする。

目指す状態は次の一文で表せる。

> **ある変更を加えるとき、「何が壊れうるか」を、コードを全部読まずに機械的に答えられる。**

## 駆動軸が変わると、何が変わるのか

駆動軸は境界の評価基準を決める。他の駆動軸だったら、境界は違う場所に引かれる。

| 駆動軸 | 境界の引き方 | 今回は |
| --- | --- | --- |
| スケール性 | 負荷特性が違うものを切り離す（読み取り多／書き込み多） | 該当しない |
| チーム自律性 | 組織構造に合わせて切る（コンウェイの法則） | 該当しない（1人開発） |
| 障害隔離 | 重要度・可用性要求が違うものを切り離す | 副次的 |
| デプロイ独立性 | リリースサイクルが違うものを切り離す | 副次的 |
| **変更の波及範囲** | **変更理由が同じものを同じ側に置き、違うものを分ける** | **これ** |

したがって本プロジェクトでは、境界を評価するとき次を最優先する。

1. **変更理由の一致** — 同じ理由で同時に変わるものは、同じ境界の内側に置く
2. **越境の可視性** — 境界を越える依存が、数えられる形（契約）になっている
3. **影響の追跡可能性** — 「このテーブルを変えたら誰が困るか」に機械的に答えられる

逆に、性能・スケール・チーム分割は評価軸から**意図的に外す**。
全部を最適化しようとすると境界が決まらないため。

## この駆動軸に対する率直な注意

**DB を分割しても、波及範囲が分からない問題が自動的に解決するわけではない。**
原因は複数あり、DB 分割が効くのは一部だけである。

| 波及範囲が分からなくなる原因 | DB 分割は効くか |
| --- | --- |
| (a) 共有テーブルを多数のモジュールが直接参照している | **効く。** これが本命 |
| (b) 外部キー・トリガ・ビュー・ストアドが DB 内で絡み合っている | **効く。** 分離すると絡められなくなる |
| (c) 変更影響を機械的に調べる手段がない（依存グラフ・静的解析がない） | 効かない。分割とは別に用意が必要 |
| (d) ドキュメントがない、または腐っている | 効かない |

さらに重要な罠がある。

> **共有DB を共有API に置き換えただけでは、結合の場所が移動しただけで波及は止まらない。**

境界を越える契約（API・イベント）が漏れやすい設計だと、
「DB を分けたのに、結局あちこち直さないといけない」状態になる。
これは分割の失敗としてよくある帰結であり、
**Phase D（データとやり取り）で契約の設計を手を抜かないこと**が条件になる。

## 結果

- Phase C-3（サービス境界の比較）の評価軸を、上記3点を最優先として設定する
- Phase G（検証）で「波及範囲が制御できているか」を測る方法を定義する。
  例：あるテーブル定義を変えたとき、修正が必要なファイル・モジュールの範囲を実測する
- 分割しても解決しない (c)(d) については、検証レポートに
  「分割で解決した範囲」と「別途必要な対策」を区別して記載する
