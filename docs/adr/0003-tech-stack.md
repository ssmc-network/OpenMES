# ADR-0003: API 実装スタックの選定

- ステータス: 提案中（未決）
- 日付: 2026-08-19

## 背景

DB は PostgreSQL で確定している。その手前の API 層をどの技術で実装するかが未決。
候補は以下の3つ。

- Python + FastAPI
- Go + Gin
- C# + ASP.NET Core Minimal API

本プロジェクトは検証プロジェクトであり、評価軸は「性能」ではなく
**検証仮説を最短で検証しきれるか**に置く。

## 評価軸

| 軸 | 重み | 理由 |
| --- | --- | --- |
| マイグレーションのスキーマ分離への適合 | 高 | 4サービス分のスキーマを独立管理する必要がある |
| 再帰CTE / 生SQL の書きやすさ | 高 | ロットトレースが再帰CTEに依存する |
| 4サービス分の実装速度 | 高 | 同じ骨格を4回作る |
| API定義・契約テストの容易さ | 中 | サービス間契約が検証対象 |
| テストでの依存サービススタブ化 | 中 | NFR-11 |
| 実運用MESとの近さ | 低 | 今回は検証が目的 |

## 候補比較

### Python + FastAPI

- SQLAlchemy 2.0 + Alembic。Alembic は `version_table_schema` でスキーマごとの独立管理が容易
- 生SQL / 再帰CTE を素直に書ける
- OpenAPI が自動生成され、契約テストに乗せやすい
- pytest + testcontainers でロール単位の接続テストが書きやすい
- 4サービス分の実装が最も速い
- 弱点：実行性能、型の緩さ（性能は本検証の主眼ではない）

### Go + Gin

- 軽量・高速。コンテナ起動が速く、E2E の回転が良い
- sqlc / pgx で型安全に生SQL を扱える。再帰CTEとの相性は良い
- マイグレーションは golang-migrate 等でスキーマ別に管理可能
- 弱点：ボイラープレートが多く、4サービス分の実装量が増える。OpenAPI は手動寄り

### C# + ASP.NET Core Minimal API

- EF Core の `DbContext` が「1サービス = 1スキーマ」に綺麗に対応する
  （`HasDefaultSchema()` でスキーマを固定でき、越境が構造的に起きにくい）
- マイグレーションも DbContext 単位で独立する
- エンタープライズ MES の実運用に最も近い
- 弱点：再帰CTE は生SQL に落とす必要がある。実装のセットアップがやや重い

## 決定

**未決。** 利用者の判断を待つ。

暫定の推奨は **Python + FastAPI**。
検証プロジェクトとして「仮説の検証」に集中でき、
4サービス分の骨格を最短で立ち上げられるため。
性能は検証仮説に含まれていない（H1〜H5 のいずれも言語性能に依存しない）。

ただし「実運用 MES に近い形で確かめたい」という意図が強い場合は
C# + ASP.NET Core Minimal API が最も適合する（EF Core のスキーマ分離が仮説と直結する）。
