# ADR-0005: DB のみ先に分割し、プロセス分割は第2ラウンドとする

- ステータス: 採用
- 日付: 2026-08-19
- 対応ステップ: A-1（どこから作り始めるか）

## 背景

マイクロサービス化の最初の分岐は「モノリスから始めるか、最初から分割するか」である。
本プロジェクトは以下の事情を持つ。

- 検証対象が「**DB リソースの分割が成立するか**」そのものである
- MES というドメインは業界で確立しており、完全な未知ではない
- 学習が目的であり、分散システムの難しさに実際に当たること自体に価値がある

## 決定

**プロセスは1つのまま、DB のスキーマと接続ロールだけを先に分割する**
（Database-first decomposition）。

- 各モジュールは自分専用の DB ロールでのみ接続する
- ロールには自スキーマ以外の権限を与えない。**越境は DB が拒否する**
- プロセス分割（独立デプロイ・ネットワーク越しの通信）は
  **第2ラウンド**として、DB 分割の検証が済んでから明示的に行う

## 検討した代替案

### 案1: 最初から分割して作る（Microservices First）

分散の難しさに最初から当たれるが、ドメイン理解が浅い段階で境界を固定するため
手戻りコストが最大になる。最頻出の失敗である**分散モノリス**
（1操作で全サービスを同期呼び出しする構造）のリスクが最も高い。→ 棄却

### 案2: モジュラーモノリスから切り出す（Monolith First / Strangler Fig）

実務での定石。境界の修正コストが最小で、ドメイン理解が深まってから分割できる。
しかし本プロジェクトが検証したい DB 分割に到達するのが最も遅い。

また案2の最大の失敗パターンは「**切り出せないモノリス**」である。
1プロセス・1スキーマでは越境が物理的に可能なため、
「後で分ける」と言いながらモジュール間で直接テーブルを参照し、
トランザクションをまたいでしまい、分割時に全部書き直しになる。→ 棄却

## 決定の理由

1. 検証したい仮説（DB 分割の成否）に最短で当たれる
2. **案2 の最大の弱点（規律が崩れて切り出せなくなる）を、DB の権限機構で構造的に潰せる。**
   規約ではなく仕組みで強制するため、締切前でも破れない
3. プロセス分割を第2ラウンドとして明示的に行うことで、
   **「DB を分けただけでは分散システムにならない」**という学びが体験として得られる
4. 重点領域（トランザクション境界とアプリ層の接続）が、
   1プロセス → 複数プロセスの移行で最も鮮明に見える

## この選択が抱えるリスクと、その扱い

案3 には固有の失敗パターンがある。**回避策を先に決めておく。**

| リスク | 内容 | 対処 |
| --- | --- | --- |
| R-A | **「DB を分けたから分割できた」と早合点する。** 1プロセス内ではトランザクションが閉じるため、Saga なしでも整合性が取れてしまい、プロセス分割時に崩れる | 第1ラウンドの検証結論に「プロセス分割は未検証」と必ず明記する。第2ラウンドまでは仮説を支持と判定しない |
| R-B | **モジュール間を細粒度のメソッド呼び出しで繋いでしまう。** 後からネットワーク越しにすると往復が爆発して移行できない | モジュール間の呼び出しは最初から「ネットワーク越しにできる粒度」で設計する。具体的な制約は Phase E-3 で決める |
| R-C | **複数スキーマにまたがる更新を1トランザクションでやってしまう。** 同一 DB インスタンスなので技術的に可能で、うっかりできてしまう。やった瞬間に分割の意味が消える | これを構造的に防ぐ仕組みを Phase E-3 で決める（未決） |

R-C は本決定の**最も危険な穴**である。第1ラウンドの実装に入る前に必ず対処方式を決めること。

## 結果

ロードマップが2ラウンド構成になる。

- **第1ラウンド**：1プロセス・N スキーマ。DB 分割の成否を検証する
- **第2ラウンド**：プロセスを分割し、ネットワーク越しの通信・部分障害・
  Saga・デプロイ独立性を検証する

Phase D-3（通信方式）と D-4（整合性の担保方式）は、
第1ラウンドでは「モジュール間の同期呼び出し」で足りてしまうが、
**第2ラウンドを見据えて第1ラウンドの時点で設計しておく**必要がある。
第1ラウンドで手を抜くと R-B / R-C に直行する。
