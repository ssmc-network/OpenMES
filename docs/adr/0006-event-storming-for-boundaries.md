# ADR-0006: サービス境界の発見手法にイベントストーミングを採用する

- ステータス: 採用
- 日付: 2026-08-19
- 対応ステップ: B-1（境界の発見手法）

## 背景

サービス境界を「どう引くか」の前に、「どうやって分け目を見つけるか」の手法を決める必要がある。
手法によって出てくる境界が変わるため、これ自体が設計判断である。

## 決定

**イベントストーミング**（ドメインイベント起点）を主軸に境界を発見する。

業務で起きる出来事を過去形で洗い出し、時系列に並べ、
イベントの塊と転換点から境界を見つける。

## 検討した代替案

### 案2: ビジネスケイパビリティ分解

組織の能力単位で分解する。境界が安定し、チーム分割と一致させやすい。
しかし粒度が粗くなり、データの流れやトランザクション境界が見えないため、
C-4（集約とトランザクション境界）で作り直しになる。
また「組織図をそのままサービスにする」失敗を招きやすい。→ 棄却

### 案3: サブドメイン分析（コア/支援/汎用）

どこに労力をかけるかの判断には有効だが、境界の「引き方」の具体性が低く、
単独では使えない。案1との併用を提案したが、今回は案1のみで進める。
スコープが広がりすぎた場合に再導入を検討する。→ 今回は不採用

### 案4: データ駆動（エンティティのクラスタリング）

最も速く機械的だが、業務の意味ではなく現在のデータ構造に境界が支配される。
**これはマイクロサービス化の典型的な失敗パターンそのもの**であり、
テーブルを見てサービスに割ると、ほぼ確実に分散モノリスになる。→ 棄却

ただし**検算としては有効**である。イベントから引いた境界に対し、
「このデータとこのデータは本当に別トランザクションでよいか」を
突き合わせる用途で、Phase C-4 での利用を検討する。

## 決定の理由

1. **D-1（データ所有権）が同時に決まる。**
   「イベントを発生させた者がそのデータを持つ」という原則で決まるため、
   Phase D の作業が大幅に軽くなる
2. 本プロジェクトの検証対象は「DB を分けられるか」であり、
   **トランザクション境界の発見が本丸**である。
   イベントは「何が同時に起きるか」を可視化するため C-4 に直結する
3. 第2ラウンド（プロセス分割・非同期化）で、
   洗い出したイベントがそのまま設計資産になる

## 想定される失敗と、その回避

| 失敗パターン | 内容 | 回避策 |
| --- | --- | --- |
| CRUD イベントの羅列 | 「品目が作成された/更新された/削除された」ばかりになると、ただのテーブル一覧であり境界が見えない | 業務的に意味のある状態変化のみを拾う。「なぜそれが起きると誰が困るか」を言えないイベントは落とす |
| 粒度の不一致 | 「ボタンが押された」（UI操作）と「在庫が引き当てられた」（業務事実）が混在する | 粒度の基準を先に決め、逸脱したものは分割・統合する |
| 実装イベントへの直結 | 洗い出したイベントをそのまま実装のイベントにすると、内部実装の変更が全サービスに波及する | 分析用イベントと公開イベントを区別する（Phase D-3 で扱う） |

## 結果

Phase B-2 以降は以下の順で進める。

1. **混沌の探索** — 思いつく限りのドメインイベントを洗い出す
2. **時系列に並べる** — 因果関係の順に整理し、矛盾やホットスポットを見つける
3. **転換点の特定** — 業務の意味が切り替わる箇所を特定する（境界の最有力候補）
4. **境界の候補を引く** — 転換点とイベントの塊から Bounded Context の候補を作る
