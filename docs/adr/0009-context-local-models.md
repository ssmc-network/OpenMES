# ADR-0009: 概念はコンテキストごとに別モデルとして定義する

- ステータス: 採用
- 日付: 2026-08-19
- 対応ステップ: B-3（ユビキタス言語）

## 背景

MES では「ロット」「品目」「オーダー」「数量」が、文脈によって異なる意味を持つ
（詳細は `docs/11-ubiquitous-language.md`）。

特に顕著なのは「オーダー」で、生産指示にとっては工程と所要材料を持つ集約だが、
製造実行と在庫にとってはただの参照キーでしかない。

この非対称性をどう扱うかで、変更の波及範囲が決まる。

## 決定

**コンテキストごとに別モデルを持つ。**

同じ「品目」でも、`master` の `Item`、`order` の `OrderItem`、
`inventory` の `StockItem` を別の型として定義し、
それぞれ必要な属性だけを持たせる。

**同じ型を複数のコンテキストで共有しない。**

## 検討した代替案

### 案2: 共通モデルを共有する（Shared Kernel）

`Item` を共通ライブラリに1つ定義して全コンテキストで使う。
変換コードが不要で実装が速く、一貫性も保てる。

しかし**これは共有DB と構造的に同じ問題**である。
テーブルを共有する代わりに型を共有しているだけで、波及範囲は止まらない。
ADR-0007 で挙げた「共有DB → 共有API」の罠の一種であり、
**駆動軸（変更の波及範囲の局所化）に真っ向から反する。**

実務では、共有ライブラリが肥大化して誰も消せなくなる、
バージョン更新が全サービスの同時デプロイを強制する（＝分割の意味が消える）
といった失敗が典型的である。→ 棄却

なお、金額型や日付型のような**変更されないプリミティブ**に限れば
Shared Kernel は許容される。この例外は必要になった時点で個別に判断する。

### 案3: 正準モデル（Canonical Data Model）

全社共通の標準データモデルを定義し、各コンテキストが変換する。
外部システム連携が多い場合には有効だが、
正準モデルが「全員の要求の和集合」になって巨大化する。

ESB / SOA 時代の代表的な失敗パターンであり、
正準モデルの変更が結局全体に波及するため、
案2 と同じ問題を変換層1枚挟んで再現することになる。→ 棄却

## 決定の理由

駆動軸が「変更の波及範囲の局所化」（ADR-0007）である以上、
案2・案3 は駆動軸に反する。**共有モデルこそが、
波及範囲を分からなくしている原因**だからである。

また今回は案1 の恩恵が特に見えやすい。
「オーダー」は生産指示にとって太い集約だが、実行と在庫にとっては文字列キーである。
案1 なら実行側は `order_no: string` だけを持てばよく、
生産指示側のモデル変更が実行側に一切届かない。

## 結果

- 各コンテキストのモデルは、マスタのモデルより**明確に痩せている**べきである。
  痩せていない場合、本当にその属性が必要か問い直す
- 変換（マッピング）コードが必要になる。これは引き受けるコストとする
- **コンテキスト間の一貫性の問題**（マスタで名称を変えても、
  スナップショットを持つ側には反映されない）が業務として発生する。
  隠さず業務ルールとして扱い、同期方針は Phase D-2 で決める
