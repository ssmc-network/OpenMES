# 01. 検証計画

## 1. 背景

MES（製造実行システム）は、製造業の現場で「計画（ERP/生産管理）」と「設備（PLC/SCADA）」の間に位置し、
製造オーダーの展開、作業実績の収集、在庫・ロットの追跡、品質記録などを担う。

MES がマイクロサービス化しにくいと言われる理由は主に以下である。

1. **参照の密結合** — 品目・工程・BOM といったマスタが、ほぼ全ての業務トランザクションから参照される
2. **トランザクション境界の広さ** — 「作業完了を記録する」という1操作が、実績計上・材料消費・在庫更新・ロット採番を同時に伴う
3. **トレーサビリティ要件** — ロットの前後追跡は、材料から製品への系譜を横断的に辿る必要がある
4. **現場の可用性要求** — ラインを止められないため、サービス間の同期依存が増えるほどリスクが増える

これらを踏まえ、「MES において Database per Service は成立するのか」を実際に作って確かめる。

## 2. 検証仮説

| ID | 仮説 | 検証で否定されうる点 |
| --- | --- | --- |
| H1 | MES のコアトランザクション（生産指示・実績・在庫/ロット）は、サービスごとに独立したデータストア境界に分割できる | どこかで cross-schema JOIN が不可避になる |
| H2 | マスタ（品目・BOM・工程）への参照は、スナップショット / 参照データ複製で解決でき、共有DBに戻す必要はない | マスタ参照が多すぎて実質的に共有DBと変わらなくなる |
| H3 | 実績計上と在庫更新の整合性は、分散トランザクションなしに Saga と冪等性で担保できる | 補償処理の実装量・複雑度が実用の閾値を超える |
| H4 | ロットの前方/後方トレースは、分割後も単一サービス内で完結し、実用的な性能で成立する | トレースが複数サービスを跨いで N+1 になり、性能が実用外になる |
| H5 | 複数サービスを跨ぐ参照（オーダー進捗照会）は、API composition で実用的な応答時間に収まる | 集約に必要な呼び出しが多すぎて読み取りモデル（CQRS）の導入が必須になる |

**H1〜H5 が全て成立すれば仮説は支持される。いずれかが崩れた場合、その理由と回避策を検証結果として記録する。**

なお本プロジェクトは「マイクロサービス化を成功させること」ではなく
「成立するかを見極めること」が目的である。**棄却も成果**として扱う。

## 3. 検証方式：スキーマレベル分離

### 3.1 なぜスキーマ分離なのか

Database per Service の教科書的な実装は「サービスごとに別DBインスタンス」だが、
本検証の主眼は**論理的な境界が守れるか**であり、物理分離のインフラコストは本題ではない。

そこで **単一 Postgres インスタンス上に、サービスごとのスキーマと専用ロールを作る**方式を採る。

```
postgres (1 instance)
├── schema: mes_master      ← owner/user: mes_master_svc
├── schema: mes_order       ← owner/user: mes_order_svc
├── schema: mes_execution   ← owner/user: mes_execution_svc
└── schema: mes_inventory   ← owner/user: mes_inventory_svc
```

### 3.2 分離を「強制」する

規約（コードレビューで気をつける）ではなく、**DBの権限機構で越境を拒否する**。

- 各サービスは自分専用のロールでのみ接続する
- そのロールには**自スキーマ以外の USAGE 権限を与えない**
- 結果として、他スキーマへの `SELECT` は `permission denied for schema` で失敗する
- スキーマを跨ぐ外部キー制約は**張れない**（張ろうとすれば設計段階で気づける）
- `search_path` は自スキーマのみに固定する

これにより「気づかないうちに越境していた」が構造的に起こらなくなり、
**分割が成立しているかどうかが実行時に自動判定できる**状態になる。

### 3.3 この方式の限界（正直に記録しておく）

| 項目 | スキーマ分離 | 物理DB分離 |
| --- | --- | --- |
| 越境アクセスの遮断 | ○（ロール権限で強制） | ○ |
| スキーマ跨ぎ FK の禁止 | ○ | ○ |
| 障害の独立性 | ×（インスタンス障害は全滅） | ○ |
| 個別のスケール・チューニング | ×（共有リソース） | ○ |
| DBエンジンの個別選択 | × | ○ |
| バックアップ/リストアの独立 | △ | ○ |

**したがって本検証で確認できるのは「論理的な分割可能性」であり、
「運用上の独立性」は検証範囲外である。**これは検証レポートに明記する。

将来的に物理分離へ移行する場合、接続文字列の差し替えのみで済むよう、
アプリ側は「自分のスキーマにしか繋がっていない」前提でのみ実装する。

## 4. 成功基準

| ID | 基準 | 判定方法 |
| --- | --- | --- |
| SC-1 | 各サービスのDBロールが、他サービスのスキーマにアクセスできない | 越境SELECTが `permission denied` になることをテストで証明 |
| SC-2 | 定義した全ユースケース（UC-01〜UC-10）が、cross-schema SQL なしで完遂する | E2Eテストが全て通る（越境すればDBが拒否するので自動的に検出される） |
| SC-3 | 3階層以上のロット系譜に対し、前方/後方トレースが正しい結果を返す | トレース専用の検証データセットでの結果一致テスト |
| SC-4 | 在庫サービス障害時、実績計上のSagaが補償され、データが不整合にならない | 障害注入テスト（在庫サービス停止 → 実績計上 → 状態検証） |
| SC-5 | 同一操作の二重実行でデータが二重計上されない | 冪等キーによる重複リクエストテスト |
| SC-6 | オーダー進捗照会（UC-10）が実用的な応答時間に収まる | p95 レイテンシを計測し閾値と比較（閾値は Phase 1 で確定） |

## 5. 棄却基準

以下のいずれかに該当した場合、その項目について仮説は棄却されたものとして記録する。

- **R1** — いずれかのユースケースで、cross-schema JOIN を使わずには実装できない
- **R2** — マスタ参照のためのAPI呼び出しが1リクエストあたり多発し、キャッシュなしでは実用外になる
- **R3** — Saga の補償処理が、同等機能をモノリスで書いた場合と比べて著しく複雑になる（目安：関連コード量が5倍以上）
- **R4** — ロットトレースが単一サービス内で完結せず、サービス跨ぎの再帰呼び出しが必要になる
- **R5** — UC-10 の応答時間が閾値を超え、読み取りモデル（CQRS）の導入なしには成立しない

棄却された場合も「なぜ成立しないか」「どの粒度なら成立するか」を記録する。

## 6. 計測項目

検証の結論を定量的に裏付けるため、以下を計測・記録する。

| 分類 | 計測項目 |
| --- | --- |
| 分離の健全性 | 越境アクセス試行の検出数（0であるべき）、スキーマ跨ぎFKの数（0であるべき） |
| 結合度 | サービス間API呼び出しの本数、ユースケースあたりの跨ぎ呼び出し回数 |
| 実装コスト | サービス別のコード行数、整合性担保（Saga/Outbox/冪等）に費やしたコード行数の比率 |
| 性能 | 主要ユースケースの p50 / p95 レイテンシ、ロットトレースの階層数別実行時間 |
| 整合性 | 障害注入時の不整合発生件数、補償完了までの時間 |

## 7. フェーズ計画

| フェーズ | 内容 | 完了条件 |
| --- | --- | --- |
| Phase 0 | 要件定義・ドメインモデル・アーキテクチャ設計 | 本ドキュメント群のレビュー完了 |
| Phase 1 | 基盤構築：Postgres スキーマ/ロール、マイグレーション、Docker Compose、CI | SC-1 を満たすテストが通る |
| Phase 2 | master サービス + order サービス（UC-01〜UC-03） | オーダー登録がマスタ検証込みで通る |
| Phase 3 | inventory サービス（UC-04 引当、UC-08 入庫） | 引当・在庫更新が冪等に動く |
| Phase 4 | execution サービス + Saga（UC-05〜UC-07） | SC-4, SC-5 を満たす |
| Phase 5 | ロットトレース（UC-09）・進捗照会（UC-10） | SC-3, SC-6 を満たす |
| Phase 6 | 検証レポート作成 | 仮説 H1〜H5 の判定と根拠データを提示 |
